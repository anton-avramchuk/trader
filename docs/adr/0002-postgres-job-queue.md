# 0002. PostgreSQL как source of truth и очередь задач

**Статус:** принято

## Контекст
Импорт, агрегация, прогоны движков, research и бэктест — долгие операции. Kafka, микросервисы и лишняя инфраструктура запрещены ТЗ (§79).

## Решение
Таблица `jobs` в PostgreSQL, отдельный worker-процесс, захват задач через `SELECT … FOR UPDATE SKIP LOCKED`. Прогресс публикуется в UI через WebSocket. Всё поднимается через Docker Compose (PostgreSQL 18, api, worker, web). Однопользовательский режим без auth до MVP-10.

## Последствия
- Задачи переживают рестарт; статус связан с `experiment_runs`.
- Пропускная способность ограничена, но достаточна для 3–4 инструментов.

## Уточнения (реализация)

- **Захват** — `SELECT … FOR UPDATE SKIP LOCKED` по самой ранней готовой задаче (`run_after <= now()`). Операции владельца (heartbeat, завершение, освобождение) проверяют `locked_by`, поэтому потерявший задачу worker не может её перезаписать. Все сравнения времени идут по `now()` БД, а не по часам процессов.
- **Статусы:** `queued` → `running` → `succeeded` / `failed` / `cancelled`.
- **Heartbeat** пишется отдельным потоком, чтобы долгая задача без вызовов прогресса не считалась зависшей. Задача без heartbeat дольше `stale_after` (30 с) возвращается в очередь, пока не исчерпаны `max_attempts` (3), иначе `failed`. **Обработчики должны быть идемпотентны** — восстановление выполняет задачу заново (для импорта это обеспечивают дубликаты/конфликты, ADR-0005).
- **Ошибка обработчика** = `failed` без автоповтора; повторяются только задачи потерянного worker'а. Политика повторов — позже, по необходимости.
- **Отмена:** ожидающая задача отменяется сразу; выполняющая получает `cancel_requested` и останавливается на ближайшем `report_progress()` / `check()` / `wait()`.
- **Штатная остановка** (SIGTERM): обработчик прерывается, задача сразу возвращается в очередь, **не тратя попытку**, — ждать таймаут не нужно.
- **Неизвестный тип задачи** worker проваливает с понятной ошибкой, а не оставляет в очереди навсегда.
- **Расписания** — интервальные (`interval_seconds` от `next_run_at`), без cron. Новый запуск не создаётся, пока предыдущая задача расписания активна; пропущенные интервалы не накапливаются, сетка запусков сохраняется.
- **Прогресс в UI:** WebSocket `/ws/jobs/{id}` опрашивает БД (по умолчанию 0,5 с) и шлёт состояние при изменении, закрываясь по завершении (код 4404 — задачи нет). LISTEN/NOTIFY — возможная оптимизация, для одного пользователя не нужна.
- Настройки worker'а — переменные `TRADER_WORKER_*` (`POLL_INTERVAL`, `HEARTBEAT_INTERVAL`, `STALE_AFTER`, `HOUSEKEEPING_INTERVAL`, `WORKER_ID`).
